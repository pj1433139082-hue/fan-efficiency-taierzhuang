## 5. 已知约束（影响后续绑定与调度）

1. **加载端零依赖（2026-10-19 版）**：`python_model.pkl` 与 `logic_bundle.pkl` 里的类与函数都按**值**内联，下载 `service` 目录后直接 `mlflow.pyfunc.load_model` 即可，不需要 `custom_sources` 注入、也不需要 `infra/` 在 `sys.path` 上。已验证：在 sys.path 无本仓库任何目录的干净进程里加载并预测，输出 `eta_excel=0.651352` / `eta_corrected=0.673609`，与 `src/model.py` 逐字一致。首版 Run `d9b9625…` 仍需要注册（保留作对照）。
2. **数值入参模型的定位**：平台本期只做批量/托管调用；`model_lab` 框架的 `publish`/`verify-publication` 只支持 `serving.mode = point-code`（点码模型），所以本模型**不走**框架发布通道，`lifecycle_state` 停在 `releasable`，不归档进 `models/NN_名称/`。平台身份以本文档为准。
3. **口径**：平台生效读 `eta_excel`（Excel 口径），与 `requirements-output-caliber` 决定一致；`eta_corrected` 为并列输出。
4. **海拔**固定 38.5 m（0~50 m 对效率影响 <0.1 个百分点）。
5. **平台参数值写整数在旧 Run 上会失败（2026-10-20 发现，同日已重传修好）**：平台按「参数值」JSON 组 DataFrame，`"motor_power": 64` 这种整数值推断成 `int64`，而 MLflow 的 schema 校验只放行 `itemsize <= 6` 的整数转 `double`，训练任务会在 `predict` 之前抛 `Incompatible input types for column 'motor_power'. Can not safely convert int64 to float64.`。两个处置：①在该 Run 上把参数值写成小数（`64.0`、`30.0`）；②重传新 Run —— `scripts/deploy-kit/fan-efficiency-taierzhuang/deploy.py` 的 `enable_tolerant_input_schema()` 已把 5 个输入列的声明类型放宽为 `any`（列名与顺序不变），本地验证整数与小数都能预测且数值一致（`eta_excel=0.651352`）。**2026-10-20 已重传**：新 Run `26df4cd3…` 的 `mlflow.log-model.history` 五个输入类型均为 `any`，`int64` 与 `float64` 两组同值入参预测 `equals=True`（`eta_excel` 均 `0.704913`）；平台部署配置已于 2026-10-20 换绑到新 Run 并试运行成功，平台上整数与小数都能直接填；旧 Run（`5fd59ee0…`）只在做对照时才会碰到，届时仍要写小数。
